# 13. 组合贷 / 公积金贷款：是否纳入范围

Status: wontfix（2026-11-14 范围裁定：不纳入本产品；理由与边界见文末「裁定」）
Type: grilling
Priority: P3
数据角色: 范围决策 —— 若纳入则参与测算
Blocked by: —

## 背景

当前房贷场景只覆盖纯商业贷款。实际业务里常见的组合贷（商贷 + 公积金）在现金流上等价于
两条并行的摊销计划再求和，但会牵出：不同利率来源、不同期限、不同还款方式、提前还款分别
处理、以及 §2.2 的 DTI 口径是否合并计算。

需要先决定「做 / 不做 / 只做展示」，再谈实现。

## 要讨论的问题

1. 本产品的范围是否只做商贷？若只做商贷，README 与本 issue 都要写下这个边界。
2. 若做组合贷：是否允许两笔不同期限与不同还款方式？
3. DTI 是否按两笔月供之和计算（合并后仍 ≤ 50%）？
4. 公积金利率是否走同一套 LPR 机制（答案是否，需要独立的固定利率输入）。

## 验收标准（决策本身）

- 产出一段结论：纳入 / 不纳入 / 分期，以及理由。
- 若纳入，拆出实现 issue；若不纳入，在 `spec.md` 的非目标里写明。

## 裁定（2026-11-14）

**不纳入本产品范围**，理由按「核心指标是参与测算的数据本身」原则（M-01/M-02）：

1. 组合贷的现金流 = **两笔并行摊销计划之和**，商贷与公积金的利率来源、期限、还款方式互相独立——「一笔测算」的要素模型（LeaseElement / 单一 principal + 单一利率）装不下，硬塞就是 `principal × 2` 的口径污染。
2. DTI 合并口径（两笔月供之和 ≤ 50%/60%）是 C 类读数，§2.2 的 DTI 定义绑定「月房贷支出」单一合同；为合并读数引入两套要素违背 M-03（不得为读数引入不参与测算的字段）。
3. 公积金利率不走 LPR（固定利率、独立政策定价），房贷表单的 LPR + 加点机制不适用，需要第二套利率录入——表单复杂度翻倍换来的只是一个「求和器」，两笔各自跑一遍本产品就能分别得到。
4. **边界写法**：本产品 v1 = 单笔合同测算器（商贷 / 融资租赁各一表单）；组合贷用户对两笔分别测算后自行加总月供与总额。README 与本 issue 即此边界的记录；若用户提出真实需求，再拆实现 issue（那时先裁定「两笔并行 + 读数合并」的要素模型，而不是直接开做）。
