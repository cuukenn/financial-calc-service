# 01. 把「测算速度」变成可重复的基准与真闸门

Status: resolved（2026-11-12，`calc-testkit/.../RunCostBaselineTest.java`）
Type: task
Priority: P1
口径影响: 不改要素、不改口径、不改任何输出数值 —— 只加测量
Blocked by: —

## 背景

设计文档写着性能闸门 **G6：120 期 P99 < 50 ms**（`docs/superpowers/specs/2026-11-02-financial-calc-service-design.md:55`，另见 `:987-988`、`:1048`、`:1092` 提到 JMH），但全 pom 里**没有 JMH、没有任何计时测试**。唯一跑得出耗时的是 `calc-testkit` 的 `ConservationPropertyTest`（jqwik `@Property(tries = 500)`，期数 1..120，`calc-testkit/src/test/java/io/github/cuukenn/fincalc/testkit/ConservationPropertyTest.java:28-37`），surefire 报 75.55 s —— 那是属性测试的总耗时，不是闸门读数，也没人读它。

2026-11-12 用一次性探针实测（未进仓库，见 `spec.md` 的基线表）：120 期全链路 **424 ms**，其中指标装配线 389 ms；480 期 1797 ms；1200 期 + 400 段 10564 ms。**闸门被超约 8 倍，而且没有任何测试会发现这件事。**

## 要做什么

1. 在 `calc-testkit` 落一个**可重复的耗时基线测试**（不需要 JMH 也能起步：固定输入、预热轮、best-of-N 或中位数、断言阈值）。至少钉住四组形态：
   - 120 期固定利率（`THIRTY_360`，无规则集）—— 这是 G6 原闸门那一格；
   - 480 期固定利率 —— 房贷上限（UI 闸门 480 月）；
   - 480 期 + 160 段分段利率（R150 的 3 个月重定价形态）；
   - 1200 期 + 400 段 `ACT_360` —— 引擎上限 `LeaseElement.MAX_PERIODS = 1200`（`calc-domain/.../model/LeaseElement.java:26`）的最坏形态。
2. 测试要**分段计时**（schedule 生成 / 现金流表 / 指标装配线 / 校验器），否则下一次回归查不出是哪一段变慢。
3. 闸门先按**实测现状**设（120 期 ≤ 450 ms 这种「不倒退」闸门），把它标成现状闸门；**不要**第一天就把 G6 的 50 ms 写成红灯 —— G6 留到 02/03 做完再收紧，收紧那一格写进 04 的验收里（见下）。
4. 基线数字写进测试注释与本 spec，注明来源与日期，让后一次改动有对照物。

## 验收标准

- `mvn -o test` 里出现这个耗时测试，且它在当前代码上**通过**（不倒退闸门），不是红灯长挂。
- 同一台机器连跑三次，波动 < 20%（否则阈值不可信，先解决抖动再谈优化）。
- 分段计时能指出 480 期那一格的时间落在哪一段（当前应是指标装配线）。
- 测试本身不改任何生产代码，不改任何输出数值。

## 涉及文件

`calc-testkit/src/test/java/io/github/cuukenn/fincalc/testkit/`（新增耗时测试）、`.scratch/calc-perf/spec.md`（把实测表换成测试读数）。

## 收尾（2026-11-12）

`calc-testkit/src/test/java/io/github/cuukenn/fincalc/testkit/RunCostBaselineTest.java`：单 @Test，四格形态，每格先跑预热再采样；每次采样都跑一次「分阶段编排」（摊销表生成 → 现金流表 → 指标装配线 → 校验器）与一次 `facade.calculate()` 全链路（1200 那一格只门阶段，见下）；取各阶段与全链路的最优读数；测试开头打印 `java` 版本与核数，每格打印一行读数。**不改任何生产代码。**

形态与输入（固定、可复现）：`EQUAL_INSTALLMENT`、月频、IN_ARREARS、本金 2 380 000、名义年利率 3.50%、`residualHandling=SEPARATE`；分段形态 3 期一段、逐段在 0.035 / 0.036 之间换率（保证每段都触发重解），规则行 `priority` 递增、`principalPlan=INHERIT`。每格在计时前还断言形态本身：期数、`schedule.hasErrors()` 为 false、末期余额 `compareTo(ZERO) == 0`、分段形态的第 1 期 / 第 `CYCLE_MONTHS + 1` 期 / 末期的 `appliedRate` 命中预期段。

三次独立运行的读数（毫秒，Java 11.0.28，10 核本机，预热后最优）：

| 形态 | schedule | 现金流表 | 指标装配线 | 校验器 | 阶段合计 | 全链路 |
|---|---|---|---|---|---|---|
| 120 期固定 `THIRTY_360` | 0.4 / 0.4 / 0.4 | 0.1 | 380.9 / 379.0 / **377.5** | 0.1 | 381.4 / 378.5 / **378.1** | 427.3 / 428.2 / **421.6** |
| 480 期固定 `THIRTY_360` | 0.7 / 0.7 / 0.6 | 0.2 | 1807.8 / 1800.3 / **1586.4** | 0.3 | 1809.1 / 1801.1 / **1587.5** | 1809.4 / 1801.4 / **1782.9** |
| 480 期 + 160 段 `THIRTY_360` | 2.4 / 2.0 / 2.5 | 0.2 | 1794.9 / 1795.3 / **1587.5** | 0.3 | 1797.6 / 1797.6 / **1590.5** | 1797.6 / 1797.6 / **1765.2** |
| 1200 期 + 400 段 `ACT_360` | 6044.7 / 6041.6 / **5869.3** | 0.4 | 4111.0 / 4322.0 / **4231.5** | 0.8 | 10156.8 / 10311.9 / **10101.9** | 只门阶段 |

波动（第三列取三次中最优，作为写入门槛的参考读数）：120 期全链路 427.3 / 428.2 / 421.6 → **极差 1.5%**；480 期固定 1809.4 / 1801.4 / 1782.9 → 1.5%；480 期分段 1797.6 / 1797.6 / 1765.2 → 1.8%；1200 期阶段合计 10156.8 / 10311.9 / 10101.9 → **2.1%**。全部远小于本 ticket 要求的 20% —— 阈值可信，可以直接当回归门用。

写入门槛（不倒退天花板，参考读数 + ~2.5× 余量，供慢机器与 CI 抖动使用）：120 期 150 / 150 / 1000 / 250 / 1400 / 1200 ms；480 期固定 300 / 300 / 4000 / 500 / 5200 / 5000 ms；480 期分段 700 / 300 / 4000 / 500 / 5200 / 5000 ms；1200 期分段 9000 / 1000 / 12000 / 1000 / 25000 ms（不设全链路门）。另两条相对门：分段 480 全链路 ≤ 固定 480 全链路 × **1.35**（实测 ~0.99，即分段几乎免费）；1200 期 `ACT_360` 阶段合计 ≤ 480 期分段全链路 × **8.0**（实测 ~5.7，留余量）。

诚实记录（AGENTS.md §6 N-02）：**闸门没有达标 G6。** 120 期全链路 ~422 ms vs G6 的 50 ms（`docs/superpowers/specs/2026-11-02-financial-calc-service-design.md:55`），**超约 8.4 倍**；测试注释里写的也是「天花板不是目标」，不得把它读成达标。

一条实测副作用（已写进 ticket 04）：1200 期那一格的摊销表阶段 5.9 s 盖过指标装配线 4.2 s —— 在 `ACT_360` 分段形态下，热点排名 1（重复求根）与 2（每段重解）的先后**互换**。第一版把该门设成 6000 ms 时，测试如实报红灯（6044.7 > 6000），门提到 9000 并在注释里写明「这 5.9 s 正是 ticket 04 (b) 要降的东西，留余量不是承认它合理」。
